## 2. cfmt

`crates/ocio-ops/src/cfmt.rs` expands a finite `m·2^e` to all of its decimal digits with
integer arithmetic and rounds half to even on them, so every conversion is exact by
construction. What differs between the libraries is ported from their sources: UCRT
spells NaN `nan`, `-nan(ind)` (negative quiet NaN without payload), `nan(snan)`,
`-nan(snan)`, `-nan`; glibc prints `nan`/`-nan`. `OStringStream` follows libstdc++'s
`_M_insert_float` and MSVC's `num_put::do_put`: the format is `%.*{f|e|E|g|G}`, MSVC uses
`%F` for uppercase fixed, padding follows `adjustfield`, width resets after every
insertion, and `float` is promoted to `double`.

Left out on purpose, because OCIO never asks for them and the libraries disagree on them
(review findings F3 and F4): the alternative form (`#`, `std::showpoint`: UCRT writes
`i.nf` for `%#.0f` of infinity, MSVC's streams drop `showpoint` for non-finite values, and
glibc's `%#.Ng` loses a digit when rounding carries into a new power of ten, `%#.2g` of
99.5 being `1.e+02`); `std::showpos` (C++ ignores it for unsigned values); `%a`; and padding
text or with a fill that is not ASCII (C++ counts bytes). `Spec::parse` refuses `#`, and the
stream refuses to pad anything but ASCII.

`Crt::NATIVE` (and `Flavor::NATIVE` for parsing) exists only for x86_64 Windows (MSVC) and
x86_64 Linux (glibc); any other target is a compile error, as is `ocio-testkit::crt`.

`crates/ocio-testkit/src/crt.rs` is the FFI reference (`snprintf`, `strtod`/`strtof`/`strtol`
and their `_l` "C"-locale variants); it is the one allowed `unsafe` path. Its self-tests
cite the C17 clause behind each expected value, or take it from the runtime.

## 3. Number parsing

`number_utils.rs` ports both branches of `NumberUtils.h`. The two wheels parse differently,
and each wheel does what the port predicts (`number_utils_oracle.rs`). The `.spi1d` reader
takes whatever parses from its 64-byte token buffer; the CLF reader requires the whole token:

| Input | Windows `.spi1d` | Windows CLF | Linux `.spi1d` | Linux CLF |
|---|---|---|---|---|
| `-0x10` | -0.0 (reads `-0`) | error (reads `-0` only) | -16 | -16 |
| `0x-5` | -5 | -5 | 0 (reads `0`) | error |
| `+-5` | -5 | -5 | error | error |
| `0x` | error | error | 0 | error |

| Input | Windows (`from_chars`) | Linux (`strtod_l`) |
|---|---|---|
| float `1e-40` (subnormal) | loads | error (glibc ERANGE) |
| CLF `1e999` | inf (stored on `out_of_range`) | 0 (value not assigned) |
| CLF `1e-310` | subnormal | 0 |
| `nan(123)` | payload dropped | payload kept |
| `long` | 32 bits | 64 bits, base 0 octal (`010` = 8) |

UCRT's own `strtod`/`strtof` are not correctly rounded: they keep 768 significant digits
with no sticky bit, and this UCRT rounds some exact float ties up (`39315.267578125` →
`0x47199345`). The Windows wheel never calls them, and in all 577 double and 702 float
cases where UCRT disagreed with the port, the wheel agreed with the port.

`StringUtils` (`string_utils.rs`) works on byte strings, as C++ `std::string` does (F6).

## 4. S1: the YAML emitter

`crates/ocio/src/yaml_cpp/` ports yaml-cpp 0.8.0's emitter: `ostream_wrapper`, `RegEx`
and `Exp`, `EmitterState` with its settings, the utils (plain-scalar validity, quoting,
escapes, literal blocks, lenient UTF-8), and `Emitter` with its `PrepareNode` state
machine. `Emitter::put` stands for `operator<<`, mapping each Rust type to the overload C++
picks (`u8` is `char`). Strings are bytes (`Emitter::write_bytes`, `&[u8]`), and
`Emitter::c_str()` returns the bytes up to the first NUL, as OCIO's `out.c_str()` does.

The S1 tests read each `serialize()` text with a test-only reader on `saphyr-parser`
events (`tests/common/yaml_tree.rs`). saphyr reports no collection style, but a flow
collection's span starts at its `[` or `{`, and an empty block collection's bracket starts
its own line. `tests/common/ocio_writer.rs` then replays OCIO's writer: `save(Config)`
(`OCIOYaml.cpp:5033-5419`) section by section with the same `Newline`s, `Literal` for
multi-line text after `SanitizeNewlines`, each value written as the C++ type OCIO uses
(`bool`, `char`, `float`, `double`, string), and `SetDoublePrecision(15)`,
`SetFloatPrecision(7)`. In the edge-case tests the emitter gets the exact numbers of the
spec, not the text read back. The tests catch a wrong precision (checked by hand): double
precision 17 fails the built-in configs, and float precision 8 fails both edge-case tests.

Some texts can't be read back into the strings the config held: a flow map's long key, a
noncharacter in a quoted or literal scalar, a literal block with a CR or a leading space,
and anything that is not UTF-8. These are replayed by substitution, as the review's
verifier did: the tree comes from the same config with a placeholder in the string's place,
and the writer puts the string back.

The fixtures come from new oracle commands (the card calls the probe `yaml_emit`):
`serialize_built_config` builds a config through the Python setters from a JSON spec and
returns `serialize()`, and `serialize_built_config_to_file` returns the bytes of
`serialize(fileName)` and `getCacheID()` for strings given as bytes. The regen group
`yaml_emitter` writes each case's spec and text:

| Case | Covers |
|---|---|
| `empty` | `Config()`: `{}` and `[]` in block and flow positions |
| `block_strings`, `flow_strings` | ~90 strings needing quotes or escapes as block values, flow sequence items and flow map values |
| `keys` | the same kinds of strings as environment, role and display keys, including 1,024- and 1,025-byte keys |
| `long_strings` | values of 1,000 to 5,000 bytes in block and flow context |
| `descriptions` | 33 multi-line, empty, newline-only and quoted descriptions, as literal blocks, interchange attributes and view descriptions in flow maps |
| `non_ascii` | Latin-1, CJK, RTL, astral, C1 controls, NEL, NBSP, LS/PS, BOM, U+FFFD, private use, U+10FFFF |
| `numbers` | special and precision-edge doubles and floats as luma, allocation variables, matrices and allocation transforms |
| `subst_flow_long_keys` | FileRules and ViewingRules custom keys of 1,024 to 1,200 bytes |
| `subst_noncharacters` | U+FDD0, U+FDEF, U+FFFE, U+FFFF, U+1FFFE, U+1FFFF, U+10FFFE, U+10FFFF, plain, quoted, literal and in flow maps |
| `subst_literal_blocks` | literal blocks with a leading space or tab, CR, CR LF, LS |

Each `subst_` case catches a mutation that the other tests miss (checked by hand): `{ ? `
for `{ ?`; dropping either noncharacter replacement; treating CR as a line break in
literal blocks; writing `|2` for a first line that starts with a space.
`s1_byte_strings.rs` (live) covers the strings that are not UTF-8 and catches `c_str()`
not stopping at a NUL, and plain scalars written through `from_utf8_lossy`.

## 5. yaml-cpp behaviors OCIO depends on

The port reproduces all of these; several are surprising.

1. **Precision below round trip.** yaml-cpp defaults to `max_digits10` (9 and 17,
   emitterstate.cpp:24-25). OCIO lowers them to 15 and 7, so `serialize()` does not
   round-trip doubles or floats. Ties round to even: 123456789012344.5 becomes
   `123456789012344`, 999999999999999.5 becomes `1e+15`.
2. **Global locale.** Numbers go through a `std::stringstream` that is not imbued
   (emitter.h:154-199). A host that sets `std::locale::global` to a locale with a comma
   decimal point or digit grouping would change OCIO's `serialize()`. The same holds for
   `repr()` and op cache IDs. The port always writes the classic format.
3. **NaN is `.nan`** whatever its sign or payload, and infinities are `.inf`/`-.inf`, so
   YAML output is platform-independent although iostream NaN text is not.
4. **Long keys.** A key over 1,024 bytes (bytes, not characters: 513 × "é" is long) is
   written `? key` / `: value` (emitter.cpp:728). A display's view list then starts on the
   `: ` line (`: - !<View> {...}`).
5. **Flow-map long keys have no space after `?`.** A FileRules or ViewingRules custom key
   over 1,024 bytes is written `{ ?key: v}` (emitter.cpp:410-439), which a reader takes as
   the plain key `?key`: `serialize()` does not read back.
6. **Empty containers** are forced to flow (emitter.cpp:205-262). If block style was
   requested, the bracket goes on its own indented line (`environment:\n  {}`); if flow
   was requested, it stays on the key's line (`active_displays: []`).
7. **Plain scalars** (emitterutils.cpp:155-199). A string is quoted if it is a null
   spelling (`~`, `null`, `Null`, `NULL`, but not `nULL`), starts with an indicator, ends
   with a space, or contains `: `, ` #`, a tab, a break, a BOM, a non-printable character
   (C0 controls, DEL, U+0080-U+009F except NEL) or any `&`. `true`, `yes`, `1.5`, `0x10`
   and `.inf` stay plain. In flow context `,[]{}` also force quotes: `a,b` is plain as a
   block value and quoted in a flow sequence.
8. **Double-quoted escapes** (emitterutils.cpp:319-364): `\" \\ \n \t \r \b \f`, `\xNN` for
   the other C0 controls and U+0080-U+00A0, `\ufeff` for a BOM. DEL is written raw even
   inside quotes.
9. **Noncharacters become U+FFFD only in quoted and literal scalars.** Those writers decode
   code points (emitterutils.cpp:90-132) and replace U+FDD0-U+FDEF, U+xFFFE/U+xFFFF,
   surrogates and anything above U+10FFFF; a plain scalar writes the same bytes as they are.
10. **Literal blocks** (emitterutils.cpp:366-380) have no indentation indicator and write
    every code point raw. A description whose first line starts with a space or a tab
    serializes to YAML that no parser reads back ("did not find expected key"), and a CR
    inside comes back as a plain line break.
11. **Strings are bytes.** OCIO accepts any bytes for its strings (the C API takes
    `const char *`; Python `bytes` pass through), and a Latin-1 config re-serializes its raw
    bytes. Plain scalars write them as they are; quoted and literal ones decode them
    leniently (a bad byte becomes U+FFFD). An overlong `C0 80` decodes to U+0000, which a
    literal block writes raw, and OCIO writes `ostream << out.c_str()` (OCIOYaml.cpp:5447):
    `serialize()` and the config cache ID (Config.cpp:5264-5270) stop there, so two configs
    whose descriptions differ only after it have the same cache ID. A NUL passed to a setter
    ends the string (`"a\0b"` is stored as `a`).
12. **`family_separator`** goes through `Write(char)` (emitterutils.cpp:382-407): letters
    plain, other printable ASCII quoted (`" "`, `"#"`), `"` and `\` escaped.
13. **`SettingChanges` restore first to last** (setting.h:85-88), so a setting changed
    twice in one scope ends at its middle value. OCIO never does this; ported anyway.
14. **Newline-only descriptions.** `saveDescription` tests the raw text for emptiness and
    then `SanitizeNewlines` strips it, so `"\n"` is written `description: ""`.
    `SanitizeNewlines` reads `back()` of the emptied string, which is undefined behavior that
    happens to work.
15. **Ordering comes from OCIO, not yaml-cpp.** The environment is sorted (`std::map`),
    roles are merged case-insensitively and sorted, and a rule's custom keys are sorted.

## 6. Platform differences

1. **NumberUtils parsing** differs between the wheels (section 3).
2. **iostream NaN text.** Windows writes `nan`, `-nan(ind)`, `nan(snan)`, `-nan(snan)`,
   `-nan`; Linux writes `nan`, `-nan`. This shows in `repr()`, in messages that print a
   NaN, and in op cache IDs, which hash the text. Processors whose ops hold NaN
   parameters therefore have different cache IDs on the two platforms. The port follows
   `Crt::NATIVE`.
3. **`serialize(fileName)`** writes through a `std::ofstream` in text mode
   (`bindings/python/PyConfig.cpp:243-249`), so the Windows file has CRLF line endings and
   the Linux one LF (the review's example: 142 bytes against 133). `serialize()` and the
   cache ID are the same on both.
4. **The Windows wheel's C++ runtime.** It loads MSVCP140.dll from System32 (14.51.36247;
   Python ships only vcruntime140), so its iostream behavior follows the installed VC++
   runtime. For example, recent MSVC STL drops `showpoint` for non-finite values
   (DevCom-10519861). OCIO never sets `showpoint`, and cfmt leaves it out.
5. **YAML output is identical** on both platforms: all 49 committed fixtures pass
   `oracle check-all` on Linux.

## 7. Mismatches and their causes

None is open.
- **UCRT `strtod`/`strtof` versus the port:** UCRT bugs (section 3). The wheel settled every
  case in the port's favor.
- **Found by the review, fixed:**
  - F1: the emitter took `&str` and `c_str()` assumed UTF-8, while OCIO's strings are
    bytes. Now bytes throughout, with wheel-backed tests (section 4).
  - F3, F4: cfmt disagreed with the libraries on options OCIO never uses: glibc's `%#g`
    carry (40 of 42.5M comparisons), UCRT's `i.nf` against MSVC's streams, `showpos` on
    unsigned values (`+5` against `5`), and padding non-ASCII text by characters. Those
    options are removed (section 2).
- **In development:**
  - glibc NaN-payload errno was a port bug, fixed before commit.
  - Malformed tokens from the CLF generator were a test bug.
  - A newline-only description written as `""` was a gap in the replay model, not in the
    emitter.
- **The emitter** needed no fix for any text OCIO produces: the built-in configs, the edge
  fixtures, the byte strings and the 10⁷ sweeps passed as ported.

## 8. Not done, open questions, owner decisions

**Not verified end to end against the wheel.** These use only cfmt primitives that were
checked against printf:
- the CTF writer's widths (row 6);
- the LUT writers (row 7);
- GPU `getFloatString` (row 8).

Each can be probed through the wheel: `GroupTransform.write`, bakers, `GpuShaderDesc`.

**Not implemented:** `sscanf`, `istream >> int` (`StringToInt`), `std::stoi`/`stoul`, and
yaml-cpp's `decode` (rows 14-17). `ParseUtils.cpp`'s number helpers and
`ParseUtils_tests.cpp` are not ported. `Config::serialize(fileName)`'s text mode is
modeled only in the test.

**Decisions for the owner:**
1. **NOTICE.** The yaml-cpp port is a derivative of MIT-licensed code. The notice is in
   `crates/ocio/src/yaml_cpp/mod.rs`; it should probably also go in `NOTICE`.
2. **yaml-cpp's own tests as expected values.** The 142 ported yaml-cpp tests take their
   expected text from yaml-cpp's test suite, which is neither the oracle nor OCIO's tests.
   Accept them as upstream tests of a vendored dependency?
3. **Classic locale assumed** for yaml-cpp, `repr()`, cache-ID streams and
   `StringUtils::SplitByWhiteSpaces` (section 5 item 2).
4. **Parity for output that does not read back** (section 5 items 5, 10 and 11): keep
   copying OCIO?
5. **Platform NaN text** in `repr()`, messages and cache IDs follows the platform (D12).
   Confirm.
6. **`saphyr-parser` =0.1.0** (MIT OR Apache-2.0; brings `arraydeque` 0.5.1 and `thiserror`
   2.0.21) is a dev-dependency of `ocio` only. PLAN.md §9 names it for the loader.
   cargo-deny was not run locally (not installed); the licenses are on the allow list.
   `xxhash-rust` (already pinned) is now also a dev-dependency of `ocio`.
7. **`StringUtils.h` status.** Review finding F6 asked for "partial"; with every function
   now on byte strings, `upstream-map.toml` keeps "done", and its note names the locale
   assumption. Say if it should read "partial".
8. **Chunk sizes.** `number_utils` (~1,000 lines) and emitter part 2 (~1,700 lines) exceed
   the ~600-line guide.
9. **Pre-existing formatting diff.** `xtask/src/fixtures.rs` is not rustfmt-clean at the
   base commit, so `cargo fmt --all --check` flags it. It is outside this card and was
   left unstaged.
10. **`cargo xtask ci` in the container.** It cannot run in the Rocky container from a git
    worktree: the submodule's gitdir lies outside the mount. It ran on Windows; clippy,
    the tests and `oracle check-all` ran in both places.
