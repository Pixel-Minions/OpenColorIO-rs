# Spike S4: CPU dispatch, Lut3D profiles and half conversion

Implementer B, 2026-09-29, revised after verifier C's review. Card: `docs/cards/phase0.md`,
section S4. Machine: AMD Ryzen 9 9950X3D (Zen 5, family 26, model 68). Platforms: Windows 11
and Rocky Linux 9.8 (Docker under WSL2, kernel 6.6.87).

## Summary

- **Lut3D forward is bit-exact.** Tetrahedral and trilinear, F32 RGBA, match the wheel bit for
  bit on Windows and in Rocky 9 at ten grid sizes from 2 to 129. That covers random, identity
  and extreme LUTs, all 65,536 half values, special values and 2^20 random values.
  - Three of the sizes (6, 32, 64) have a `size − 1` that isn't a power of two, so the input
    scaling rounds.
- **The verifier confirmed it independently.** Verifier C checked the port against the wheel's
  own SSE2, AVX, AVX2 and AVX-512 kernels, called directly. It also checked CPUInfo against
  upstream's constructor on 200,000 synthetic CPUID tables, and the half conversions against
  compiled Imath 3.2.1 and `SSE2.h` over every input. No divergence anywhere.
- **The wheel runs the AVX-512 tetrahedral kernel here.** Single-pixel calls run the scalar path
  instead. Trilinear always runs the SSE2 code path.
- **CPUInfo matches the wheel.** The port's CPU detection prints exactly what the wheels'
  `ociocpuinfo` prints, on both platforms.
- **The profiles form two numeric classes.**
  - The FMA profiles, AVX2 and AVX-512, are identical to each other.
  - The others, generic, SSE2 and AVX, are identical to each other except for the sign of some
    exact zeros.
  - The two classes differ in the last bits, and by far more near cancellation (up to 270,770
    ulp on a random LUT).
- **Half conversions.** SSE2's software conversion and F16C agree for every input in both
  directions. Imath 3.2.1 differs from both only on signaling NaNs, and so does the `half`
  crate.
- **The card's EPYC 9V45 quirk is not in 2.5.2.** It landed upstream after the release, and the
  wheels don't contain it, so the port leaves it out.

**The limits of the Imath wheel tests.** The F16 and F32 casts multiply by 1.0
(`CPUProcessor.cpp:38-41`), which quiets signaling NaNs before and after Imath. So these tests
check rounding and every other value, but they can't tell Imath from F16C on signaling NaNs.
The verifier's checksums of the compiled Imath cover that (below).

**The F32 → F16 floats:**
- every finite half;
- the midpoint to the next half, and the floats either side of it, with both signs;
- 20 NaN payloads;
- the specials;
- 2.4 million random values.

**Probes per LUT check** (`probe_pixels`):
- all 65,536 half values, cycled through RGBA;
- 20³ = 8,000 combinations of 20 special channel values: ±0, ±NaN, signaling NaN, ±Inf, a
  denormal, values next to 0.5 and 1.0, 2, −1, 1e30 and ±FLT_MAX;
- 262,144 random pixels (1,048,576 values): three quarters uniform in [−0.25, 1.25), one quarter
  random bit patterns.

**The LUTs:**
- random: uniform in [−0.5, 1.5);
- identity;
- extreme: ±FLT_MAX, ±1e30, denormals, ±0, ±65504 and random finite bit patterns.

The LUTs go to the wheel as `setValue` calls, so their values are finite: JSON can't carry NaN
or ±Inf.

**CPUInfo, checked by hand.** The port's `CpuInfo::instance()`, printed in `ociocpuinfo`'s format,
is byte-identical to the wheels' `ociocpuinfo` on Windows and in Rocky 9. That includes the brand
string with its trailing spaces. The automated form of this check needs the `cpu_info` oracle
command, which is stuck in a git stash (see [Open questions](#open-questions-for-the-owner)).

### Verifier C's independent checks

These ran from scripts in `target/verify/`, which is not committed:

- **Lut3D against the wheel's own kernels.** The wheel's `applyTetrahedral{SSE2,AVX,AVX2,AVX512}`
  were called directly through the DLL and SO entry points (`wheel_probe.py`,
  `tests/verify_c_probes.rs`). Each matched the port's profile of the same name, at sizes 2, 5,
  17, 32, 33, 64 and 129, on both platforms.
  - This covers the SSE2, AVX and AVX2 kernels, which the wheel never picks on this CPU.
  - It also covers the processor at row widths 1, 2 and 16.
- **CPUInfo.** `CpuInfo::from_cpuid` equals upstream's CPUInfo constructor, compiled verbatim
  with CPUID test doubles, on 200,000 synthetic CPUID tables (`c_ref/cpuinfo_ref.cpp`,
  `tests/verify_c_cpuinfo.rs`). That covers every quirk branch.
- **Half conversions.** Checksums over every input of Imath 3.2.1's real `half.h` (no lookup
  table, compiled without F16C), of `SSE2.h`'s conversions compiled verbatim, and of F16C equal
  the checksums of the Rust ports (`c_ref/half_ref.cpp`, `tests/verify_c_hash.rs`). This is the
  evidence for Imath's signaling-NaN behavior that the wheel tests can't see.
- **Disassembly of both wheels.**
  - Each library has 108 FMA instructions: 72 in the Lut1D kernels and 36 in the Lut3D AVX2 and
    AVX-512 kernels. The scalar, SSE2, AVX and trilinear code has none, so no compiler fused a
    multiply-add anywhere else.
  - Each has 24 F16C instructions, all in the Lut1D kernels' half stores. So Imath's inline
    `half` conversions are the software ones everywhere.

## The wheel's CPU flags and kernels

`ociocpuinfo` compiles upstream's CPUInfo.cpp with the library's generated `CPUInfoConfig.h`.
Its output is the same from both wheels:

```
name           : AMD Ryzen 9 9950X3D 16-Core Processor
vendor         : AuthenticAMD
hasSSE2 1  SSE2Slow 0  hasSSE3 1  SSE3Slow 0  hasSSSE3 1  SSSE3Slow 0  hasSSE4 1  hasSSE42 1
hasAVX 1  AVXSlow 0  hasAVX2 1  AVX2SlowGather 0  hasAVX512 1  hasF16C 1
```

**Build switches.** Every `has*()` is `OCIO_USE_* && flag`, so both official x86-64 wheels are
built with `OCIO_USE_SSE2/SSE3/SSSE3/SSE4/SSE42/AVX/AVX2/AVX512/F16C` all on. That matches
CMake's defaults for `AMD64`/`x86_64`, and it is the port's `BuildConfig::X86_64_WHEEL`.

**CPU flags.**
- Zen 5 is family 0x1A, which is above upstream's "Zen 3 and earlier" gather cut-off
  (`family <= 0x19`). So AVX2 isn't flagged as slow.
- XCR0 is 0xe7 on Windows, and `ociocpuinfo` reports AVX-512 in WSL2 too, so the OS enables
  the AVX-512 state on both.

**Kernels:**

| Call | Kernel |
|---|---|
| Tetrahedral, `numPixels > 1` | `applyTetrahedralAVX512` (FMA) |
| Tetrahedral, `numPixels <= 1` | the scalar branch of `Lut3DTetrahedralRenderer::apply` (`Lut3DOpCPU.cpp:427`) |
| Trilinear | the `OCIO_USE_SSE2` branch of `Lut3DRenderer::apply`, fixed at compile time with no runtime dispatch |

- **Row width decides `numPixels`.** The CPU processor hands each image row to the first op
  (`ScanlineHelper.cpp:119-150`). So a width-1 image runs the scalar tetrahedral path for every
  pixel. The port's renderer takes the same decision from the pixel count of each call.
- **No EPYC 9V45 quirk.** The card asks for "AVX-512 blocked on EPYC 9V45". That is upstream commit
  `c2bd98f7` (PR #2324, 2026-07-08), which is on `main` but is not an ancestor of `v2.5.2`
  (2026-05-13). Neither wheel's `OpenColorIO` library or `ociocpuinfo` binary contains the string
  "EPYC". The port matches 2.5.2 and does not block AVX-512 there.
- **Forced profiles are test-only.** `CpuInfo::with_flags` and `CpuInfo::with_build` are
  `#[doc(hidden)]`. They exist so the tests can run a numeric profile this machine wouldn't pick,
  as upstream's test runner forces SIMD modes.

## The Lut3D numeric profiles

Each C++ kernel is its own renderer, written as exact scalar code, one SIMD lane per pixel. The
lanes never mix: the RGBA transposes only move bits, and each gather reads its own lane's index.

What the port reproduces:
- **LUT copy.** `createOptLut` sanitizes values: NaN becomes 0 and ±Inf becomes ±FLT_MAX. It
  pads each entry to RGB0 in SSE2 builds, so the SIMD code can load 4 floats.
- **Layout.** Blue index fastest, as `Lut3DTransform::setValue` stores it.
- **Clamping and indices.** SSE `_mm_min/max_ps` semantics (NaN becomes 0), with float index
  arithmetic.
- **Floors.** SSE2 truncates; AVX and later use `_mm*_floor_ps`. These are equal on the clamped
  range.
- **Multiply-adds.** The first product is a plain multiply. The next three multiply-adds are FMA
  (`f32::mul_add`) in AVX2 and AVX-512, and a multiply plus an add elsewhere.
- **Scope.** x86 only. The SSE2NEON (ARM) variants are not ported.

On the 33³ LUTs, over all 335,680 probe pixels in one call, the profiles compare as follows
(Windows and Rocky 9 give identical tables):

| LUT | generic = SSE2 = AVX vs wheel | AVX2 = AVX-512 vs wheel | generic vs SSE2 | trilinear SSE2 vs wheel | trilinear generic vs wheel |
|---|---|---|---|---|---|
| random | 173,777 of 1,342,720 values differ (up to 270,770 ulp) | identical | identical | identical | 324,976 differ |
| identity | 2,770 differ (up to 2 ulp) | identical | identical | identical | 18,277 differ |
| extreme | 34,568 differ (up to 3,136 ulp); generic 40,419 | identical | 5,851 differ, every one +0 vs −0 | identical | 265,044 differ |

**Why the profiles differ:**
- **FMA vs non-FMA.** AVX2 and AVX-512 round each of the three multiply-adds once; the others
  round twice. The large ulp counts come from results near zero.
- **Generic vs SSE2 and AVX: signed zeros only.** In two cases, the scalar path and the SIMD
  kernels give zero weight to different vertices:
  - **An input on a grid point.** The scalar path's upper vertex uses `ceil(idx)`, while the
    SIMD kernels use `min(prev + 1, lutmax)`.
  - **Tied fractional parts.** When `fx == fz > fy`, the scalar path zero-weights n001
    (`Lut3DOpCPU.cpp:533-552`) and the SIMD masks zero-weight n100 (`Lut3DOpCPU_SSE2.cpp:140-161`).
  - The zero-weight term is `0 × v`: `−0` when the LUT value `v` is negative, `+0` otherwise.
    When the running sum is exactly `−0`, adding `−0` keeps it `−0` and adding `+0` makes it
    `+0`. So the two paths can give zeros of opposite sign.
  - **Wheel evidence** (found by the verifier, `target/verify/zero_tie.py`). A 2³ LUT with input
    (0.5, 0.25, 0.5) gives `0x80000000` in a single-pixel call and `0x00000000` in a two-pixel
    call. `fractional_tie_signed_zero` pins it.
  - Everything else is the same: the non-zero weights and their vertices, and the order of the
    sums.
- **Generic trilinear** uses `(b − a)·z + a` instead of `a·(1 − z) + b·z`. Only builds without
  SSE2 use it.
  - The Linux aarch64 wheel is probably one of them: `aarch64` matches neither `ARM64|arm64` nor
    an x86 name in CMake, so SIMD is off. That is a reading of CMake, not verified.
  - The macOS arm64 wheel uses SSE2NEON instead, which the port doesn't model. The port's
    `BuildConfig::CURRENT` maps every non-x86 target to no SIMD.

## Half conversions

OCIO has three conversions:
- Imath 3.2.1: OCIO's scalar `half`. The wheel builds Imath with
  `IMATH_HALF_USE_LOOKUP_TABLE=OFF` and its library sources without `__F16C__`, so both
  directions use Imath's bit-manipulation code.
- The SSE2 software conversion in `SSE2.h`.
- F16C, in the AVX, AVX2 and AVX-512 packs.

| Comparison | Half → float (all 65,536) | Float → half (all 2^32) |
|---|---|---|
| SSE2 scalar port vs SSE2 intrinsics | identical | identical |
| F16C scalar port (the `half` crate's software conversion) vs F16C hardware | identical | identical |
| SSE2 vs F16C | identical | identical |
| Imath vs SSE2 or F16C | **1,022 differ**: every signaling-NaN half | **8,388,606 differ**: every signaling-NaN float |

**Details of the differences:**
- **Imath keeps a signaling NaN signaling.**
  - Half to float: `0x7c01` gives `0x7f802000` in Imath, while SSE2 and F16C set the quiet bit
    and give `0x7fc02000`.
  - Float to half: Imath returns `0x7c00 | m | (m == 0)`, where `m` is the top 10 mantissa bits,
    so `0x7f800001` gives `0x7c01` in Imath and `0x7e00` in F16C and SSE2.
  - The evidence for the Imath side is the verifier's checksum of compiled Imath 3.2.1 over every
    input, which matches `ocio_ops::imath_half`.
- **Everything else is identical in all three**, including round-to-nearest-even at every
  boundary, denormals, overflow to Inf at 65520, underflow to ±0, ±Inf, and quiet-NaN payloads
  (the top 10 mantissa bits).
- **The difference can't be seen in the wheel's F16 casts.** `BitDepthCast` multiplies by
  `m_scale = 1.0f` before converting to half and after converting to float
  (`CPUProcessor.cpp:38-41`), and that multiply quiets the NaN first.
- **The `half` crate is not an exact Imath reference.** Both its F16C path and its software
  fallback force the quiet bit in both directions, so it matches F16C, not Imath. The port
  therefore has its own Imath port, `ocio_ops::imath_half`. The testkit's `all_half_values()`
  goes through the `half` crate, so its 1,022 signaling-NaN halves come out quiet: fine for
  probes, but not "exact".
- **SSE2 and AVX Lut1D kernels will agree on F16.** Because SSE2's software conversion equals
  F16C, an F16 image gets identical values from the SSE2 and AVX Lut1D kernels, as far as the
  conversions go.

## Mismatches and their causes

There is no unexplained mismatch against the wheel. The differences found:

1. **Between profiles**, as described above. They are expected; the wheel matches the profile
   dispatch picks.
2. **`f32::mul_add` vs the FMA instruction, with NaN operands.**
   - With more than one NaN operand, the instruction returns the first NaN in encoding order,
     which depends on the 132/213/231 form the compiler picks. `fmaf` sometimes returns a
     different one: 84 of 2.1 million triples differed, every one of them with a NaN operand.
   - OCIO's FMA kernels never see a NaN. The LUT is sanitized, the weights are in [0, 1], and
     the sums can only overflow to ±Inf. So the proof covers every non-NaN operand, including
     invalid operations such as Inf × 0.
3. **The `half` crate vs Imath**, on signaling NaNs, as described above.

## What is still not verified

The verifier's direct kernel calls and its CPUID tables close most of the gaps on this machine.
What remains:

| Not verified | Why |
|---|---|
| The generic trilinear path | Only builds without SSE2 use it, and no x86 wheel is one of them |
| The SSE2NEON (ARM) variants | Not ported; ARM is out of scope (PLAN.md D11) |
| The SSE2, AVX and AVX2 kernels in CI, and CPUInfo on real CPUs of other families | The verifier's direct calls and CPUID tables are one-off scripts in `target/verify/`, not committed tests |

**Proposal for CI coverage: Intel SDE (owner approval needed to download).**
- For each emulated chip, run the wheel's `ociocpuinfo`, the oracle and the port's test binary
  under the same CPUID:
  - `sde64 -hsw` (Haswell): AVX2 with slow gathers, so the wheel picks AVX;
  - `-skl` (Skylake client): the AVX2 kernel;
  - `-snb` (Sandy Bridge): AVX;
  - `-p4p` or `-mrm`: no AVX, so the SSE2 kernel;
  - `-skx` (Skylake-X): AVX-512.
- The port's `CpuInfo::instance()` then decodes the emulated CPUID, so the CPUInfo quirks are
  tested end to end too.
- SDE executes the instructions the host supports natively and traps CPUID, so FP results stay
  hardware-exact.

**Alternatives:**
- Commit the verifier's direct-kernel probe as an oracle command. It needs the kernels'
  addresses in each wheel binary.
- QEMU user mode (`qemu-x86_64 -cpu Haswell|Skylake-Client|Nehalem`, from EPEL) in the Rocky
  container. It is open source, but it has no AVX-512, emulates FP in software, and needs an
  install.
- WSL2 kernel parameters in `.wslconfig`. `clearcpuid=avx512f` should leave AVX-512 out of XCR0,
  so the wheel falls back to AVX2; `noxsave` leaves SSE2 only. This is a system change, for
  Linux runs only, and needs your approval.
- Real hardware: a Zen 3 (AVX kernel), a Skylake client (AVX2) and an Intel AVX-512 machine.
  This matters for the render farm: whichever kernel those CPUs pick is the one the port must
  match there.
