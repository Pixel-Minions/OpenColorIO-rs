# S2 + S5: fast math and exact math

Spike report for card S2 + S5 (`docs/cards/phase0.md`). Upstream: OpenColorIO v2.5.2. Oracle:
the `opencolorio==2.5.2` wheel. Machine: AMD Ryzen 9 9950X3D (Zen 5); Windows 11 and Rocky Linux
9.8 (glibc 2.34) under Docker on the same CPU.

## Verdict

- **Fast math is bit-exact.** `SSE.h`'s approximations are ported as exact scalar lanes
  (`crates/ocio-ops/src/sse.rs`). All 13 functions match `SSE.h` compiled by MSVC 19.44 and by
  GCC 11.5, bit for bit, on 1.67 million inputs; `sseLog2`, `sseExp2` and `ssePower` also match
  the wheel through the Log and Gamma renderers.
- **The Log and Gamma F32 CPU renderers are bit-exact against the wheel,** for every style, both
  directions, with fast math on (the default) and off, on Windows and on Rocky Linux 9. That is
  140 exact comparisons of about 1.07 million RGBA pixels each, including NaN payloads, signed
  zeros, subnormals and infinities.
- **The wheel differs between Windows and Linux in two places, and the port reproduces both**
  (PLAN.md D12). Both were found by reading the wheels' machine code before any test ran, and
  each is guarded by a test that fails if the other platform's behavior is used:
  1. `LogUtil::GetLogSideBreak` computes in `float` on Windows and in `double` on Linux
     (a C++ overload-resolution difference). It changes camera-log outputs by 1 ulp in
     about 19% of parameter sets.
  2. The scalar mirror Gamma renderers give a NaN result a different sign: GCC turned
     `copysign(1, x) * y` into an XOR of the sign bit, MSVC multiplies.

  A third detail is Linux-only: the wheel links glibc's old `log2@GLIBC_2.2.5`, whose
  compatibility wrapper returns a *positive* NaN for negative input. The port emulates it.
- **S5, exact math: no SVML and no auto-vectorization in Log or Gamma.** With fast math off,
  both wheels call the scalar math library (`log2f`, `exp2f`, `powf`), and the port, which calls
  the same functions through Rust `std`, is bit-identical on both platforms.
- **SVML appears only in PQ.** With fast math off, the Windows wheel's PQ renderers call
  MSVC's SVML `__vdecl_powf4`. It differs from `powf` in about 1.7% of values (up to 311 ulp,
  and NaN bits). Calling the same routine reproduces the wheel exactly. This needs a decision
  (see "Open questions").

Nothing is left unexplained. No check was loosened, and no port output is used as an expected
value.

## Which renderer each transform uses

At F32 in and out, each of these transforms becomes one op, and the processor applies that op's
renderer. The op data is never a no-op or an identity (for Gamma, because the exponents are not
all 1), has no simpler replacement, and the separable-prefix bake is skipped for F32 input
(`OpOptimizers.cpp:559-563`). The renderer is picked by `GetLogRenderer` (`LogOpCPU.cpp:224-315`)
or `GetGammaRenderer` (`GammaOpCPU.cpp:211-292`); fast math selects the `SSE` class.

| Transform | Op data | Renderer (fast math off / on) |
|---|---|---|
| `LogTransform(base=2)` | simple log, base 2 | `LogRenderer` / `LogRendererSSE`, scale 1 (forward); `AntiLogRenderer` / `AntiLogRendererSSE`, log2(base) 1 (inverse) |
| `LogTransform(base=10)` | simple log, base 10 | `LogRenderer(SSE)` with `LOG10_2`; `AntiLogRenderer(SSE)` with `LOG2_10` |
| `LogTransform`, any other base | 4 default parameters | `Lin2LogRenderer(SSE)` forward, `Log2LinRenderer(SSE)` inverse |
| `LogAffineTransform` | 4 parameters per channel | as `LogTransform`: default parameters with base 2 or 10 are Log2 or Log10 ops; otherwise `Lin2Log`/`Log2Lin` |
| `LogCameraTransform` | 5 parameters (6 with `linearSlope`) | `CameraLin2LogRenderer(SSE)` forward, `CameraLog2LinRenderer(SSE)` inverse |
| `ExponentTransform`, NEGATIVE_CLAMP | BASIC_FWD / BASIC_REV (inverse) | `GammaBasicOpCPU` / `GammaBasicOpCPUSSE` |
| `ExponentTransform`, NEGATIVE_MIRROR | BASIC_MIRROR_FWD / _REV | `GammaBasicMirrorOpCPU(SSE)` |
| `ExponentTransform`, NEGATIVE_PASS_THRU | BASIC_PASS_THRU_FWD / _REV | `GammaBasicPassThruOpCPU(SSE)` |
| `ExponentWithLinearTransform`, NEGATIVE_LINEAR | MONCURVE_FWD / _REV | `GammaMoncurveOpCPUFwd(SSE)` / `GammaMoncurveOpCPURev(SSE)` |
| `ExponentWithLinearTransform`, NEGATIVE_MIRROR | MONCURVE_MIRROR_FWD / _REV | `GammaMoncurveMirrorOpCPUFwd(SSE)` / `...Rev(SSE)` |

With a raw config (version 2), `ExponentTransform` builds a GammaOp; a version 1 config would
build an ExponentOp instead (`GammaOp.cpp:195-207`), which is out of this spike.

## Windows and Linux differences

### 1. `GetLogSideBreak`: `float` on Windows, `double` on Linux

`LogUtils.cpp:276-277` calls `log2` on `float` arguments. With MSVC, `<cmath>` declares the
`float` overloads in the global namespace, so the call is `log2f`. With GCC, `LogUtils.cpp` does
not include the libstdc++ `<math.h>` wrapper, which is what adds the `float` overloads to the
global namespace, so the unqualified `log2` is the C library's `double log2(double)`.
(`LogOpCPU.cpp` gets the wrapper through `MathUtils.h`, and there `log2(float)` is `log2f` on
both platforms.)

Machine code in the wheels:
- Windows, `OpenColorIO_2_5.dll` at `0x18021ac60`: two calls to `log2f`, then `divss`, `mulss`
  and `addss`. Everything is in `float`.
- Linux, `libOpenColorIO.so` symbol `LogUtil::GetLogSideBreak` (`0x4017b0`): two calls to
  `log2@plt` (double) on `cvtss2sd` arguments, then `divsd`, and `mulsd` of the rounded break
  by the `double` quotient before `cvtsd2ss`.

The port has both variants (`log_utils::get_log_side_break_msvc` and `_libstdcxx`) and picks
one with `cfg(windows)`. The break moves the linear segment's offset, so it changes every
linear-segment output of a camera log. On random parameters, 1,520 of 8,064 combinations give a
different break (1 or 2 ulp); LogC3's exact parameters happen not to.

### 2. Scalar mirror Gamma: the sign of a NaN

`GammaBasicMirrorOpCPU` and the two `GammaMoncurveMirrorOpCPU` renderers compute
`std::copysign(1.0f, in) * value`. For every finite or infinite value, both compilations are
equal. For a NaN input with its sign bit set, they differ:
- **MSVC** (`0x1801bd3d0`, loop at `0x1801bde60` for the moncurve mirror) builds `±1.0f` with bit
  operations and uses `mulss`, so the NaN keeps the sign `powf` gave it (positive, since the
  argument was `|in|`).
- **GCC** (`GammaBasicMirrorOpCPU::apply` at `0x384be0`, `GammaMoncurveMirrorOpCPUFwd::apply` at
  `0x384d30`, `...Rev::apply` at `0x385030`) uses its `xorsign` pattern, `value ^ signbit(in)`,
  so the NaN gets the input's sign. The exception is the alpha channel of the two moncurve
  mirror renderers, where GCC builds `±1.0f` with `orps` and multiplies.

The port encodes this per renderer and per channel (`gamma_op_cpu.rs`, `BASIC_MIRROR_SIGN`,
`MONCURVE_MIRROR_SIGN`). The SSE renderers are the same on both platforms: they OR the sign bit
back.

### 3. Linux: the wheel links glibc's pre-2.29 `log2`, `log` and `pow`

The Linux wheel was built against a glibc older than 2.29, so it imports `log2@GLIBC_2.2.5`,
`log@GLIBC_2.2.5` and `pow@GLIBC_2.2.5`, the SVID/XOPEN compatibility wrappers. Rust binaries
link the current `@GLIBC_2.29` symbols. Both run the same `__ieee754_*` core. The differences
are only in the error cases, and `pow`'s error results are the same values anyway. Only `log2`
is reachable from the ported code: `GetLogSideBreak` takes `log2` of
`linSlope * linBreak + linOffset`, which is negative when the break is negative, and
LogCameraTransform does not reject that. `__log2_compat` then returns `NAN` (positive, from
`__kernel_standard(x, x, 49)`), where the current symbol returns the negative x86 default NaN.
The NaN reaches the output through the linear segment. `log_utils::log2_glibc_2_2_5` reproduces
it, and the "negative break" camera case covers it. The `float` functions (`log2f`, `exp2f`,
`powf`, `logf`, `expf`) have the same symbol version in the wheel and in Rust (`@GLIBC_2.27`).

## Mismatches

None is open. Every oracle test passed on its first run on both platforms, because the
platform-specific code paths had already been read from the binaries. The only first-run
failure was my own discriminator test: LogC3's parameters give the same break in both
`GetLogSideBreak` variants, so I added base-10 per-channel cases that don't.

## S5: exact math and SVML

- **Log and Gamma.** With fast math off, the renderers call `log2f`, `exp2f` and `powf` once per
  channel. The Windows DLL calls them through the UCRT import thunks (for example, four scalar
  `powf` calls per pixel in `GammaBasicMirrorOpCPU::apply` at `0x1801bd3d0`). The port calls
  the same functions (Rust `f32::log2`, `exp2` and `powf` compile to calls to `log2f`, `exp2f`
  and `powf` on both targets), and all 140 oracle comparisons are exact, including the
  exact-math ones. An SVML substitute would show up there: in PQ, SVML differs from `powf` in
  about 1.7% of values.
- **Constant folding.** The upstream code computes no constant with a math function in the
  paths ported here. The renderers' coefficients are computed at run time on both sides.
  Test parameters go through `std::hint::black_box` so that LLVM cannot fold, for example,
  `powf(x, 1.0)`.
- **`/fp:` and FMA.** The wheel is built with MSVC's default `/fp:precise` and no `-ffast-math`.
  The Log, Gamma and fast-math code of both wheels has no FMA and no reassociation. The only
  compiler changes are commutative operand swaps and the `xorsign` rewrite above.
- **PQ uses SVML.** `FixedFunctionOpCPU.cpp:2133-2194` uses `_mm_pow_ps` when fast math is off
  and `_MSC_VER >= 1920 && OCIO_USE_AVX` (the Windows wheel). It compiles to calls to
  `__vdecl_powf4` (20 call sites in the two unrolled PQ kernels, through the thunk at
  `0x18034b0b0` to `0x18034ba20`). The Linux wheel uses the scalar `Renderer_LIN_TO_PQ<float>`
  with `powf`. I measured the difference with a throwaway experiment (not committed; PQ is WP 2.4):

  | Wheel, fast math off | Compared with | RGB values that differ (of 3,197,118) | Max ulp |
  |---|---|---|---|
  | Windows `LIN_TO_PQ` | the SSE kernel with `powf` | 53,682 finite (37,512 by 1 ulp, 16,170 by ≥ 5 ulp) and 7,383 NaN (bits) | 311 (at input 1.49e-6) |
  | Windows `PQ_TO_LIN` | the SSE kernel with `powf` | 26,793 finite (13,185 by 1 ulp, 3,438 by 2, 10,170 by ≥ 5) and 1,144,539 NaN (bits) | 568,267 (near `x = c1`, where the numerator cancels) |
  | Linux `LIN_TO_PQ`, `PQ_TO_LIN` | the scalar kernel with `powf` | 0 | 0 |
  | Windows, both | the SSE kernel with MSVC 14.44's `__vdecl_powf4` (called through an inline-asm shim) | **0** | 0 |

  `__vdecl_powf4` is defined in MSVC's `msvcrt.lib` and `libcmt.lib`, which Rust's MSVC target
  already links. The wheel was linked by MSVC 14.44, and its routine is the same machine code
  as the one in the local 14.44 `msvcrt.lib` (the first 400 instructions are identical, apart
  from addresses). Stable Rust cannot declare the call: `extern "vectorcall"` and SIMD types in
  FFI are unstable. The experiment used `asm!` with `call`. As the card asks, the port does
  not do this. The decision is the owner's (below).

## Other findings

- **Constants.** The fast-math constants are `(float)` casts of double literals. Their bits
  were read back from both wheels and match `f64 as f32`: on Linux from the loaded library's
  initialized globals (`PNLOG0-5`, `PNEXP0-4`, `EONE`, `EMASK`, `EBIAS`, `ESIGN_MASK`,
  `EABS_MASK`, ...), on Windows from 16-byte replicated constants in the DLL. The `sseAtan` and
  `sseCos` coefficients are not in the Windows DLL at all.
- **Dead code.** `sseAtan`, `sseAtan2`, `sseCos`, `sseSin` and `sseSinCos` are not called
  anywhere in OCIO 2.5.2's library, only by `SSE_tests.cpp`. So the wheel cannot check them;
  the compiled `SSE.h` check and the lane cross-check do.
- **`SSE2.h`.** The Log and Gamma renderers use nothing from `SSE2.h` (it serves pack/unpack
  and the LUTs), so this spike ports nothing from it.
- **Mirror styles and NaN.** The SSE mirror renderers compute `ssePower(|x|)`, which is 0 for
  NaN, and OR the sign back. So a NaN input gives ±0 with fast math and NaN without. This is
  upstream's behavior, and upstream's tests record it.
- **Integer outputs.** A NaN reaching `Converter<UINTn>::CastValue` is undefined behavior in
  C++. Both wheels give 0, from a 32-bit `cvttss2si`, and the port matches that (verified
  through the alpha channel).

## Not verified, or not done

- **Op data.** `LogOpData` and `GammaOpData` are ported without `validate`, `getCacheID`, the
  string accessors, `getIdentityReplacement` and Gamma's `compose`. Their messages and IDs print
  doubles with C++ stream formatting, which is WP 0.5's `cfmt`. These are WP 1.3l1 and 1.3g1.
- **Two Log tests.** `LogOpCPU/log2lin_test` and `lin2log_test` need
  `LogUtil::ConvertLogParameters`, whose validation messages print doubles. Not ported.
- **The optimizer.** "One op, unchanged" is established by reading `OpOptimizers.cpp`, not by
  asking the wheel. The O1.1 `processor_ops` oracle command will show it.
- **Other bit depths.** Only F32 input with F32 or integer output was checked. F16, and
  integer input (where the separable-prefix bake replaces the ops with a Lut1D), are WP 1.1,
  1.2 and 2.1.
- **Other platforms.** The `cfg(windows)` / `cfg(not(windows))` split stands for "the MSVC
  build" / "the GCC and libstdc++ build". macOS (libc++) and ARM are unverified (D11).
- **Speed** was not measured.

## Open questions for the owner

1. **PQ with fast math off on Windows.** Either:
   - call the same `__vdecl_powf4` from a SIMD module through a small `asm!` shim, which
     reproduces the wheel exactly with the MSVC 14.44 toolset (an oracle test would guard
     the toolset version); or
   - port a `powf` version and grant a waiver: about 1.7% of values differ, up to 311 ulp, and
     NaN bits.

   The first matches the wheel. The second is portable Rust, but not byte-exact on Windows.
2. **Emulating library quirks.** The port reproduces glibc 2.2.5's `log2` NaN sign and GCC's
   `xorsign` NaN sign so that Linux stays bit-exact, even for NaN outputs. Is that the standard
   you want everywhere (it is what D12 implies), or should NaN payload and sign differences
   become a documented waiver class?
3. **Where things live.** The spike added `op.rs` (the `CpuOp` trait, in-place `&mut [f32]`,
   per `docs/architecture.md`) and `open_color_types.rs` (`TransformDirection`,
   `NegativeStyle`) to `ocio-ops`. WP 1.2c may want to move or extend them.
4. **Commits.** The permission system denied `git commit` and `git add` in this worktree, so the
   chunks exist as a working tree plus per-chunk snapshots (see the final report). They need
   committing by someone with permission.

## Reproduction

```sh
# Oracle checks (live on first run, then cached per machine under target/oracle-cache)
cargo test -p ocio-ops --test log_oracle --test gamma_oracle
scripts/rocky9.sh cargo test -p ocio-ops --test log_oracle --test gamma_oracle

# The wheels' machine code
objdump -d --no-show-raw-insn <oracle-venv>/Lib/site-packages/PyOpenColorIO/bin/OpenColorIO_2_5.dll   # Windows, no symbols
scripts/rocky9.sh objdump -d -C --no-show-raw-insn \
    /work/target/rocky9/oracle-venv/lib/python3.13/site-packages/PyOpenColorIO/libOpenColorIO.so    # Linux, full symbol table
scripts/rocky9.sh nm -D --undefined-only <same .so>    # log2@GLIBC_2.2.5, log2f@GLIBC_2.27, ...
```

The compiled `SSE.h` check includes `src/OpenColorIO/SSE.h` unmodified, with two stub headers:
`CPUInfoConfig.h` defines `OCIO_USE_SSE2 1`, and `OpenColorIO/OpenColorIO.h` defines
`OCIO_NAMESPACE`. A harness runs each `__m128` function on inputs four at a time and each scalar
overload per lane, and writes the 13 outputs per input. It was built with
`cl /O2 /EHsc /std:c++17` (19.44.35211) and `g++ -O3 -std=c++17` (11.5.0), and compared with
the port.
