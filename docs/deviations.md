# Deviations from OpenColorIO 2.5.2

Where the port intentionally behaves differently from upstream. Each entry needs the
owner's approval. A deviation must never change an output covered by the byte-exact
definition of done (PLAN.md §3) unless it also has a waiver in `waivers.toml`.

Upstream bugs that don't affect outputs (crashes, data races, deadlocks) are fixed in the
port and listed here. Upstream bugs that do affect outputs are copied, and listed in
`docs/improvements.md` for the owner to decide on at the end.

**General rule (approved by the owner in chat, 2026-09-30):** where upstream reads or writes
memory it doesn't own (a crash, or corrupted data), the port returns an error instead. Each
case is a `U-` entry in `docs/improvements.md`, where an entry can make an exception.
The first case is D-2: image layouts that reach outside their buffer.

| Id | Upstream behavior | Port behavior | Affects outputs? | Approved |
|---|---|---|---|---|
| D-1 | iostream and yaml-cpp number formatting use the process's C++ global locale (`std::locale::global`). The LUT readers' `sscanf`/`sscanf_s` scan in the process's C locale, which Python sets at startup: under Python the Windows wheel runs in the ANSI code page's (1252), where the UCRT takes 0xA0 for white space (in the format, and what `%d` and `%s` skip first; a `%s` word still doesn't end at it), so spi1d's `Length\xa03` reads as a length of 3 there and is refused on Linux | Always formats with the classic "C" locale, and scans in it (`crates/ocio-ops/src/utils/cscan.rs`, checked against the C runtime in the "C" locale, `crates/ocio-ops/tests/cscan_crt.rs`, which also pins the Windows wheel's difference) | Formatting: only in a C++ host that changes the global C++ locale. Python and Rust hosts can't: Python's `locale.setlocale` changes the C locale, not the C++ one, and the wheel always formats with "C". Scanning: LUT files with a 0xA0 byte where the readers expect white space, read by the Windows wheel under Python (or any host that sets a C locale with more white space) | Approved by the owner in chat, 2026-09-29; scanning added by the owner, 2026-10-08 |
| D-3 | The logging function is called while the global logging lock is held (`src/OpenColorIO/Logging.cpp:75-88, 162-204`). A logging function that logs or changes the logging settings deadlocks, and so does one that waits for a lock that a logging thread holds, such as Python's GIL | The level and the logging function are read under the lock, and the function is called after it is released (`crates/ocio-ops/src/logging.rs`) | Not for what one thread logs through a logging function that doesn't log or change the logging settings: the same lines reach the same function. Otherwise: when several threads log at once, the lines of their multi-line messages can interleave, where upstream's lock keeps each message's lines together; a logging function that logs gets its own lines between the lines of the message it is receiving, where upstream deadlocks, and one that always logs recurses until the stack overflows; and after `set_logging_function` or `reset_to_default_logging_function` returns, the old function can still receive the rest of a message that another thread is logging, where upstream waits for that message to end | Approved by the owner in chat, 2026-09-30 |
| D-4 | `Platform::Strcasecmp` and `Strncasecmp` call `_stricmp`/`_strnicmp` (Windows) or `strcasecmp`/`strncasecmp` (Linux), which fold case by the process's C locale (`src/OpenColorIO/Platform.cpp`). Python sets that locale at startup, so under Python the Windows wheel folds non-ASCII bytes by the ANSI code page, byte by byte even in UTF-8 text: with code page 1252, an alias "Ě" (bytes `C4 9A`) matches "Ċ" (`C4 8A`). On Linux in a C or UTF-8 locale, ASCII only (the wheel ran in `C.UTF-8`); a single-byte Linux locale would likely fold more, like Windows (not reproduced) | Folds `A`-`Z` only, as the classic "C" locale does, everywhere (`crates/ocio-ops/src/platform.rs`); checked against the C runtime in the "C" locale for every pair of bytes (`crates/ocio-ops/tests/platform_crt.rs`). The same principle as D-1 | Only under Python on Windows (with an ANSI code page other than UTF-8), and likely in a single-byte Linux locale, for names that differ in the case of non-ASCII bytes: the lookups of names, aliases, roles, metadata attributes and file-format elements that ignore case. Linux in a C or UTF-8 locale, and hosts that don't set a locale, are unchanged | Approved by the owner in chat, 2026-09-30 |
| D-2 | An image description holds pointers and strides and is never checked against a buffer (`src/OpenColorIO/ImageDesc.cpp`); a layout that reaches outside its memory makes `CPUProcessor::apply` read or write outside it, which is undefined behaviour. The Python binding checks only a buffer's entry count, not the strides | After upstream's checks, the constructors refuse a layout that would make the CPU engine touch a byte outside its memory: "PackedImageDesc Error: The strides and dimensions reach outside the image buffer." (and "PlanarImageDesc Error: ..."). The check covers exactly the bytes the engine touches: whole rows of `4 * width` channels for an RGBA-packed image, each channel at `start + x * x_stride + y * y_stride` otherwise (`crates/ocio-ops/src/image_desc.rs`, `reaches_outside`) | Only for layouts whose use is undefined behaviour upstream. Every layout whose pixels are all inside its memory is accepted and processed as upstream does | Approved by the owner, 2026-09-30 (the image-description API proposal) |
| D-5 | `SetEnvVariable` and `UnsetEnvVariable` (`Platform::Setenv`, `Unsetenv`) change the process's environment through the C runtime (`_wputenv_s`, `setenv`, `unsetenv`: `src/OpenColorIO/Platform.cpp:99-142`), which every library of the process then sees | Rust 2024 makes changing the process environment `unsafe`, which the port's crates forbid. What OCIO sets or unsets is recorded, and replayed on the process's environment whenever OCIO reads it, with each C runtime's and system's rules (`crates/ocio-ops/src/platform.rs`, `ProcessEnv`, `EnvState`): on Windows `_wputenv_s` splits `name=value` at its first `=`, refuses a name starting with `=`, removes a variable set to "", and goes through UTF-16; the system's block folds names by its table (I-117) and the C runtime's list by ASCII (I-113); on Linux `setenv` refuses a name holding `=` and `unsetenv` removes every entry of the name. `Getenv`, `isEnvPresent` and the whole-environment load of a context see the changes; other code in the process doesn't. The process environment is read through `std::env`, which (on Linux) leaves out an `environ` entry whose only `=` is its first character, such as `=abc`, where OCIO reads a variable named "" with the value `abc`; an entry such as `=a=b` comes back whole, and OCIO reads it, as upstream, as the variable "" with the value `a=b` | Not for what OCIO reads: its variables are the same, checked against the wheel (`crates/ocio/tests/env_oracle.rs`). Other libraries, child processes and C runtime calls in the same process don't see OCIO's changes. Upstream's tests that check the change through the Windows API (`Platform_tests.cpp` `envVariable`, `getenv`, `setenv`) are ported without those checks | Approved by the owner, 2026-10-05 |
