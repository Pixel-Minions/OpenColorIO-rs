# Deviations from OpenColorIO 2.5.2

Where the port intentionally behaves differently from upstream. Each entry needs the
owner's approval. A deviation must never change an output covered by the byte-exact
definition of done (PLAN.md §3) unless it also has a waiver in `waivers.toml`.

Upstream bugs that don't affect outputs (crashes, data races, deadlocks) are fixed in the
port and listed here. Upstream bugs that do affect outputs are copied, and listed in
`docs/improvements.md` for the owner to decide on at the end.

**General rule (approved by the owner in chat, 2026-09-30):** where upstream reads or writes
memory it doesn't own (a crash, or corrupted data), the port returns an error instead. Each
case is a `U-` entry in `docs/improvements.md`, where an entry can make an exception.
The first case is D-2: image layouts that reach outside their buffer.

| Id | Upstream behavior | Port behavior | Affects outputs? | Approved |
|---|---|---|---|---|
| D-1 | iostream and yaml-cpp number formatting use the process's C++ global locale (`std::locale::global`). The LUT readers' `sscanf`/`sscanf_s` scan in the process's C locale, which Python sets at startup: under Python the Windows wheel runs in the ANSI code page's (1252), where the UCRT takes 0xA0 for white space (in the format, and what `%d` and `%s` skip first; a `%s` word still doesn't end at it), so spi1d's `Length\xa03` reads as a length of 3 there and is refused on Linux | Always formats with the classic "C" locale, and scans in it (`crates/ocio-ops/src/utils/cscan.rs`, checked against the C runtime in the "C" locale, `crates/ocio-ops/tests/cscan_crt.rs`, which also pins the Windows wheel's difference) | Formatting: only in a C++ host that changes the global C++ locale. Python and Rust hosts can't: Python's `locale.setlocale` changes the C locale, not the C++ one, and the wheel always formats with "C". Scanning: LUT files with a 0xA0 byte where the readers expect white space, read by the Windows wheel under Python (or any host that sets a C locale with more white space) | Approved by the owner in chat, 2026-09-29; scanning added by the owner, 2026-10-08 |
| D-3 | The logging function is called while the global logging lock is held (`src/OpenColorIO/Logging.cpp:75-88, 162-204`). A logging function that logs or changes the logging settings deadlocks, and so does one that waits for a lock that a logging thread holds, such as Python's GIL | The level and the logging function are read under the lock, and the function is called after it is released (`crates/ocio-ops/src/logging.rs`) | Not for what one thread logs through a logging function that doesn't log or change the logging settings: the same lines reach the same function. Otherwise: when several threads log at once, the lines of their multi-line messages can interleave, where upstream's lock keeps each message's lines together; a logging function that logs gets its own lines between the lines of the message it is receiving, where upstream deadlocks, and one that always logs recurses until the stack overflows; and after `set_logging_function` or `reset_to_default_logging_function` returns, the old function can still receive the rest of a message that another thread is logging, where upstream waits for that message to end | Approved by the owner in chat, 2026-09-30 |
| D-4 | `Platform::Strcasecmp` and `Strncasecmp` call `_stricmp`/`_strnicmp` (Windows) or `strcasecmp`/`strncasecmp` (Linux), which fold case by the process's C locale (`src/OpenColorIO/Platform.cpp`). Python sets that locale at startup, so under Python the Windows wheel folds non-ASCII bytes by the ANSI code page, byte by byte even in UTF-8 text: with code page 1252, an alias "Ě" (bytes `C4 9A`) matches "Ċ" (`C4 8A`). On Linux in a C or UTF-8 locale, ASCII only (the wheel ran in `C.UTF-8`); a single-byte Linux locale would likely fold more, like Windows (not reproduced) | Folds `A`-`Z` only, as the classic "C" locale does, everywhere (`crates/ocio-ops/src/platform.rs`); checked against the C runtime in the "C" locale for every pair of bytes (`crates/ocio-ops/tests/platform_crt.rs`). The same principle as D-1. It covers minizip-ng's `mz_path_compare_wc` too, which compares the names of an `.ocioz` archive's entries through the C runtime's `tolower` (`crates/ocio/src/minizip/mz_os.rs`) | Only under Python on Windows (with an ANSI code page other than UTF-8), and likely in a single-byte Linux locale, for names that differ in the case of non-ASCII bytes: the lookups of names, aliases, roles, displays, views, metadata attributes and file-format elements that ignore case. Linux in a C or UTF-8 locale, and hosts that don't set a locale, are unchanged | Approved by the owner in chat, 2026-09-30 |
| D-2 | An image description holds pointers and strides and is never checked against a buffer (`src/OpenColorIO/ImageDesc.cpp`); a layout that reaches outside its memory makes `CPUProcessor::apply` read or write outside it, which is undefined behaviour. The Python binding checks only a buffer's entry count, not the strides | After upstream's checks, the constructors refuse a layout that would make the CPU engine touch a byte outside its memory: "PackedImageDesc Error: The strides and dimensions reach outside the image buffer." (and "PlanarImageDesc Error: ..."). The check covers exactly the bytes the engine touches: whole rows of `4 * width` channels for an RGBA-packed image, each channel at `start + x * x_stride + y * y_stride` otherwise (`crates/ocio-ops/src/image_desc.rs`, `reaches_outside`) | Only for layouts whose use is undefined behaviour upstream. Every layout whose pixels are all inside its memory is accepted and processed as upstream does | Approved by the owner, 2026-09-30 (the image-description API proposal) |
| D-5 | `SetEnvVariable` and `UnsetEnvVariable` (`Platform::Setenv`, `Unsetenv`) change the process's environment through the C runtime (`_wputenv_s`, `setenv`, `unsetenv`: `src/OpenColorIO/Platform.cpp:99-142`), which every library of the process then sees | Rust 2024 makes changing the process environment `unsafe`, which the port's crates forbid. What OCIO sets or unsets is recorded, and replayed on the process's environment whenever OCIO reads it, with each C runtime's and system's rules (`crates/ocio-ops/src/platform.rs`, `ProcessEnv`, `EnvState`): on Windows `_wputenv_s` splits `name=value` at its first `=`, refuses a name starting with `=`, removes a variable set to "", and goes through UTF-16; the system's block folds names by its table (I-117) and the C runtime's list by ASCII (I-113); on Linux `setenv` refuses a name holding `=` and `unsetenv` removes every entry of the name. `Getenv`, `isEnvPresent` and the whole-environment load of a context see the changes; other code in the process doesn't. The process environment is read through `std::env`, which (on Linux) leaves out an `environ` entry whose only `=` is its first character, such as `=abc`, where OCIO reads a variable named "" with the value `abc`; an entry such as `=a=b` comes back whole, and OCIO reads it, as upstream, as the variable "" with the value `a=b` | Not for what OCIO reads: its variables are the same, checked against the wheel (`crates/ocio/tests/env_oracle.rs`). Other libraries, child processes and C runtime calls in the same process don't see OCIO's changes. Upstream's tests that check the change through the Windows API (`Platform_tests.cpp` `envVariable`, `getenv`, `setenv`) are ported without those checks | Approved by the owner, 2026-10-05 |
| D-6 | `Config::archive` writes the `.ocioz` archive with minizip-ng 4.0.10, deflating with zlib 1.3.1 at level 9 (`src/OpenColorIO/OCIOZArchive.cpp:205-333`). Its entries carry the time they're written (`time(NULL)` for the config) and the files' own times, as DOS dates broken down in the local time zone and as NTFS times; the files come in the order the file system lists them. Both wheels write the same deflate bytes for the same data | The container is minizip-ng's, ported (`crates/ocio/src/minizip/`): the same entries, names, order of the listing, methods, flags, made-by system and version, attributes, extra fields, CRCs, sizes and contents. The deflate streams are flate2's on zlib-rs at level 9 (owner decision 2026-10-17); measured against both wheels, they are zlib's bytes for small entries (up to 4 KiB of random data and 8 KiB of LUT text) and differ beyond (0.1-1.6% larger). The DOS dates are broken down in UTC (the port has no time zone), writing and reading. Extracting (`ExtractOCIOZArchive`), the port sets a file's attributes on Windows only as far as read-only (`SetFileAttributesW` isn't in safe Rust); the Linux modes are set as upstream sets them, and the dates too, the DOS date of an entry without NTFS times read in UTC. `crates/ocio/tests/ocioz_archive_oracle.rs` compares archives entry by entry, without the time stamps and the compressed bytes | The bytes of an archive: the deflate streams of entries past a few KiB, their compressed sizes and the offsets after them, and the DOS dates (by the time zone's offset); the times of extracted files whose entries have only a DOS date (by the same offset); the attributes of extracted files on Windows other than read-only (archive, hidden, system, ...), and so extracting again over a hidden or system file, which the wheel refuses (`CreateFile` won't replace it without those attributes) and the port does. An archive's time stamps and file order differ from run to run upstream too. Read back, by the port or by OCIO, the archives give the same configs and LUT files | Owner decision P4-3, 2026-10-07; flate2 2026-10-17; the dates in UTC and only read-only restored on extraction, accepted as recommended, 2026-10-17 |
| D-7 | pybind11 makes `pybind11_builtins.pybind11_object`, the base of every class of the module, as a C type: its C name (`tp_name`) is `pybind11_object`, its metatype `pybind11_builtins.pybind11_type`, and its instances (`sizeof(instance)`, 56 bytes) hold weak references at offset 40, before 8 bytes of flags. Its metatype `pybind11_type` and the descriptor `pybind11_builtins.pybind11_static_property` are C types too, whose methods (`__call__`, `__getattribute__`, `__setattr__`, `__delattr__`; `__get__`, `__set__`, `__delete__`) are the slot wrappers of their C slots | The port's `pybind11_object` is a PyO3 class padded to pybind11's size (`__basicsize__` 56, so that a Python class may derive from several classes of the module), whose layout puts weak references last; PyO3 names it `pybind11_builtins.pybind11_object` and makes it with the metatype `type` (`crates/ocio-py/src/pybind11.rs`, `Pybind11Object`). The metatype and the static property are made in Python (`type()`, in the wheel's dictionary order, with the same flags and sizes); their methods are Python functions that check their arguments as the slot wrappers do (a `self` of the wrapper's class by its type's MRO, named by its type's C name; no keyword arguments but `__call__`'s; the slots' argument counts, with CPython's texts) and carry the wrappers' `__doc__`, `__text_signature__`, `__objclass__`, `__name__` and `__qualname__` (p6-core re-check round 3). Making them as pybind11 does would need more `unsafe` C API calls (C slot functions, `tp_new`, `tp_dealloc`) or the values held outside the instances | Only these (`crates/ocio-py/tests/metatype_oracle.rs`, `d7_lists_what_still_differs`, checks each against the wheel, but for the frames and the hashing in (4)): (1) `type(pybind11_object)` is `type`, not `pybind11_type`. (2) Texts CPython writes with pybind11_object's C name: `OCIO.TransformDirection.__new__(int)` raises "pybind11_builtins.pybind11_object.__new__(int): int is not a subtype of pybind11_builtins.pybind11_object" (the wheel: "pybind11_object.__new__(int): int is not a subtype of pybind11_object"), `repr(pybind11_object.__init__)` is "<slot wrapper '__init__' of 'pybind11_builtins.pybind11_object' objects>" (the wheel: "... of 'pybind11_object' objects"), `pybind11_object.__init__(object)` raises "descriptor '__init__' requires a 'pybind11_builtins.pybind11_object' object but received a 'type'" (the wheel: "... a 'pybind11_object' object ..."), and `OCIO.TransformDirection.__bases__ = (object,)` raises "__bases__ assignment: 'object' object layout differs from 'pybind11_builtins.pybind11_object'" (the wheel: "... differs from 'pybind11_object'"). (3) `__weakrefoffset__` is 48, not 40, for `pybind11_object`, every class of the module, and Python classes deriving from them, with `__slots__` or several bases too. (4) The seven methods of `pybind11_type` and `pybind11_static_property` are `function` objects, not `wrapper_descriptor`s: their repr is "<function pybind11_type.__call__ at 0x...>" (the wheel: "<slot wrapper '__call__' of 'pybind11_type' objects>"); bound, as `OCIO.TransformDirection.__call__`, a `method`, not a `method-wrapper`; they have the attributes of a Python function (`__module__` "pybind11_builtins", `__dict__`, `__code__`, `__globals__`, ...), and `inspect.ismethoddescriptor` answers false for them and `inspect.isfunction` true (the wheel's: true and false; `inspect.signature` gives the same in both, from `__text_signature__`); a traceback through them shows their frames, and each call through them is a Python frame more (recursion depth); a `str` subclass with its own `__hash__` or `__eq__`, as an attribute name, is hashed and compared once per class of the MRO in the metatype's lookup (the wheel's: once). (5) `type.__setattr__` and `type.__delattr__` applied to a class of the module (or `pybind11_object`) set and delete; the wheel refuses them ("can't apply this __setattr__ to pybind11_type object", CPython's check that no C slot is jumped over), and `type.__setattr__(OCIO.TransformDirection, 'value', 3)` therefore replaces the property the metatype's `__setattr__` refuses to (U-100) | Approved by the owner, 2026-10-21 (p6-core re-check, relayed by the coordinator); the list rewritten in round 3 to what still differs, and corrected in round 4 (`inspect`, `__bases__`) |
| D-8 | A class the binding gives no `__repr__` (the iterator classes, `BuiltinTransformRegistry`, ...) prints Python's default `<PyOpenColorIO.PyOpenColorIO.Name object at 0x...>`, with the address of the Python object (`id()`) | The same text: the port's object has its own address, as each process's objects do | Only the address in such a repr; the oracle's step interpreter masks it (`" at 0x?"`) on both sides | Owner decision P6-7, 2026-10-17 (docs/cards/phase6.md) |
| D-9 | Upstream's `Config` takes no lock: a Python callback the library calls during a call on a config (the logging function, a `ConfigIOProxy` override, the hash function) can use that same config, reading it (or changing it) while the library works on it. `OCIO.SetLoggingFunction(c.getColorSpace)` then `c.validate()` of a config whose validation logs errors: the wheel's logging function looks the messages up as color spaces, and the validation succeeds | The binding holds a config's lock while the library works on it (`crates/ocio-py/src/py_config.rs`, `with_config`): a callback that uses the same config raises RuntimeError "Config: a callback of a call on this config uses it while the library works on it, which the port can't share (docs/deviations.md, D-9)", which ends the outer call as the callback's exception does. A call on the config from another thread meanwhile (the callback released the GIL, as Python code does now and then) isn't a callback of it: it waits, with the GIL released, until the first call ends, then runs (the wheel's runs alongside it); a thread that waits for something the first call's callback waits for in turn deadlocks, where the wheel's goes on. Safe Rust can't hand the callback the config the library is borrowing | Only for a callback that uses the config of the call it runs in: other configs, and everything outside callbacks, behave as upstream's. Checked against the wheel in `crates/ocio-py/tests/callbacks_oracle.rs` (`callbacks_as_the_wheels`: the wheel's validation succeeds where the port's raises, another config's validation as the wheel's; another thread's calls on the config while a validation waits in its logging function: the wheel's answers) | Owner decision 2026-10-22 (option A, relayed by the coordinator; no read/write-lock follow-up for now) |
| D-10 | pybind11's `error_already_set::what()` (`error_fetch_and_normalize::format_value_and_trace`) reads an exception's `__notes__` with `PyList_Size`, whatever the attribute is. When it isn't a list (a tuple, a `str`, `None`), `PyList_Size` fails with CPython's `PyErr_BadInternalCall`, and `what()` holds the line `FAILURE obtaining len(__notes__): SystemError: <interpreter build path>/Objects/listobject.c:342: bad argument to internal function` after the message: the path is the interpreter build machine's (a temporary directory of the user Administrator, ending in `Python-3.13.13`, with the Windows interpreter here), so it differs per interpreter build and per platform. This `what()` text is part of the message of the exceptions the library raises for a failing callback (the logging function in the config reader's message, the hash function, a `PyConfigIOProxy` override in the LUT loader's message) | The port lists no notes for a `__notes__` that isn't a list: the message is the wheel's without that line, in every other byte (`crates/ocio-py/src/callback.rs`, `format_value_and_trace`). The `[WITH __notes__]` mark after the type name is kept, as the wheel has it for any `__notes__` attribute | Only the exception message of a callback's failure, and only for an exception whose `__notes__` was set by hand to something that isn't a list (`add_note` makes a list). Checked against the wheel in `crates/ocio-py/tests/callbacks_oracle.rs` (`callbacks_as_the_wheels`: a tuple, a `str` and `None`: the wheel's message with that line removed is the port's, and every other step of the two reports is equal) | Owner decision 2026-10-22 (relayed by the coordinator): the port lists no notes there |
